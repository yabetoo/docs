## Event Types

Yabetoo currently supports the following webhook event types. Each event corresponds to a specific action that occurs on your account and can be used to trigger logic in your backend (e.g. updating order statuses, sending notifications, etc.).

## Event body

Every webhook is a `POST` request whose JSON body always has the same envelope:

| Field | Description |
|-------|-------------|
| `id` | Event identifier (`evt_…`). The same across delivery attempts: use it to ignore a duplicate. Also sent in the `X-Yabetoo-Webhook-Id` header. |
| `type` | The event type, for example `intent.succeeded`. Also sent in the `X-Yabetoo-Webhook-Event` header. |
| `data` | The event object. Its content depends on the `type` (see each event below). |
| `created_at` | Event date, in ISO 8601 format. |

## Payments (payment intents)

A confirmed [payment intent](/en/payments/api/create) produces one of these three events. For all three, `data` contains:

| Field | Description |
|-------|-------------|
| `data.intent` | The payment intent: `id`, `amount`, `currency`, `status`, `description`, `metadata`, `liveMode`, `createdAt`… |
| `data.charge` | The payment attempt: `id`, `intentId`, `amount`, `currency`, `status`, `captured`, `failureCode`, `failureMessage`, `financialTransactionId`, `externalId`… |

Find your order with `data.intent.id`, or with the `data.intent.metadata` you passed when creating the intent.

### `intent.succeeded`

Triggered when a payment has been successfully received on your account.

- **Use Case:** Confirm that a customer has completed their payment.
- **Extra fields:** `data.amountCaptured` (amount credited to your balance, fees deducted) and `data.operatorName` (`mtn` or `airtel`).
- **Typical Actions:**
  - Mark an order as paid
  - Send a confirmation email or SMS
  - Update the payment status in your database

```json
{
  "id": "evt_3kQ9xV2mLp7RtY8sWb4nZc1d",
  "type": "intent.succeeded",
  "data": {
    "intent": {
      "id": "pi_OYgGCdY1VaWvszwZcAY7VXvuXI70Ao9rsuMl",
      "amount": 5000,
      "currency": "xaf",
      "status": "succeeded",
      "description": "Order 1234",
      "metadata": { "orderId": "1234" },
      "liveMode": false,
      "createdAt": "2026-02-16T15:33:55.048+00:00"
    },
    "charge": {
      "id": "ch_ADdQhObdEDlz4L0kl7qNRniFjruNcrcY85xq",
      "intentId": "pi_OYgGCdY1VaWvszwZcAY7VXvuXI70Ao9rsuMl",
      "amount": 5000,
      "currency": "xaf",
      "status": "succeeded",
      "captured": true,
      "financialTransactionId": "7331529368",
      "externalId": "ext_7hp8lsjCFwTemoeL"
    },
    "amountCaptured": 4825,
    "operatorName": "mtn"
  },
  "created_at": "2026-02-16T15:34:20.112+00:00"
}
```

<Note>
  The body may contain fields other than the ones described here. Only rely on documented
  fields: the others may change without notice.
</Note>

### `intent.failed`

Triggered when the payment is refused: insufficient balance, customer rejection, unknown number…

- **Where to read the reason:** `data.charge.failureCode` and `data.charge.failureMessage`.
- **Typical Actions:**
  - Offer the customer to retry, possibly with another number
  - Release the reserved order or stock

### `intent.expired`

Triggered when the operator did not answer in time, most often because the customer did not approve on their phone.

- **Not necessarily final:** Yabetoo keeps checking the transaction with the operator. If the money was eventually debited, you then receive `intent.succeeded` for the same intent.
- **Typical Actions:**
  - Show "payment not confirmed" rather than "payment refused"
  - Do not immediately start a new payment for the same order

## Disbursements

### `disbursement.succeeded`

Triggered when a disbursement has been successfully processed from your account to a recipient.

- **Use Case:** Track outbound payments or automate accounting tasks.
- **Typical Actions:**
  - Notify the recipient
  - Log the transaction in your financial system
  - Update payout status in your admin dashboard

### `disbursement.failed`

Triggered when a disbursement fails, including when a review rejects it or expires (`failureCode`: `risk_review_rejected`, `risk_review_expired`, or `risk_blocked` for a disbursement held and then refused after the fact, see [Error Handling](/en/api-reference/errors#disbursement-failure-codes)). The reserved funds are released.

### `disbursement.review_opened`

Triggered when a production disbursement is held for verification before being sent to the operator. It follows `disbursement.created`; the payload carries `review` (`status: "open"`).

- **Not final:** the disbursement stays `processing`. The outcome arrives as `disbursement.succeeded` or `disbursement.failed`.
- **Typical Actions:**
  - Show "under verification" rather than "being sent" to your user
  - Do not retry the disbursement: it will be processed or canceled within 48 h

### `deposit_disbursement.review_opened`

The same event for a disbursement funded from the deposit wallet. Its outcomes are `deposit_disbursement.succeeded` and `deposit_disbursement.failed`.

The only other disbursement lifecycle event is `disbursement.created`.

## Checkout sessions

### `checkout.session.completed`

Triggered when a [checkout session](/en/payments/checkout-page/create) is paid successfully.

- **Identifier to use:** `data.checkoutSessionId` (do not rely on `data.orderId`).
- **Typical Actions:**
  - Mark the order tied to the session as paid
  - Deliver the good or service

### `checkout.session.payment_failed`

Triggered when a payment attempt on a session fails.

- **Not final:** the session stays open and the customer can retry.
- Emitted when the failure is known from the confirmation response; a timeout is carried by `intent.expired`.
- `data.error` is an opaque string, to be logged, not parsed.

<Note>
  A payment through a [payment link](/en/payments/payment-link/create) emits
  `payment_link.checkout.completed` / `payment_link.checkout.failed` instead of
  `checkout.session.*`. `checkout.session.expired` is not emitted today.
</Note>
